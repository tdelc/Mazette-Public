Point de départ

L’essentiel

En une phrase

Une application R / Shiny qui lit les fichiers Google Drive de la brasserie, les transforme en une douzaine de tables, les met en cache dans un .RData, et les affiche en quinze onglets derrière un mot de passe qui décide de ce que chacun voit.

Langage R 4.5.1, Shiny + bslib 5. Aucun build, aucun JavaScript à compiler.
Source de vérité Des classeurs Google Drive, dont un fichier d’index qui liste tous les autres.
Cache outputs/R_new_env_<date>.RData, reconstruit quand il manque.
Authentification Un mot de passe par personne, lu dans le classeur, qui ouvre un jeu d’onglets.

Lancer l’application en local

# 1. Un .Renviron a la racine, avec les trois variables (cf. Administration)
# 2. Puis, depuis la racine du projet :
R -e 'shiny::runApp()'

Au premier lancement sans cache local, l’application va chercher le .RData sur Drive ; s’il n’y est pas non plus, elle reconstruit tout depuis les classeurs. Comptez quelques minutes dans ce dernier cas.

Les cinq fichiers qui comptent

FichierRôle
global.RCharge les paquets, source tout R/, définit les constantes partagées (couleurs, seuils, ingrédients).
import.RReconstruit toutes les tables depuis Drive. Ne tourne que lorsqu’aucun cache n’est disponible.
server.RCharge les données au démarrage, puis toute la logique réactive.
ui.RLa coquille et les constructeurs d’interface de chaque onglet.
R/acces.RCatalogue des onglets, profils d’accès, et construction des onglets à la demande.
Le mode « Je veux tout savoir » ajoute : le détail de chaque table, la mécanique de chargement, le runbook d’installation complet et les pièges connus.

Ce que voit l’utilisateur

Un onglet n’est pas une page

Chaque onglet est un nav_panel construit par une fonction ui_*() de ui.R. Les gros onglets (Compta, Travail, Détail) contiennent eux-mêmes des sous-onglets via navset_card_tab. Les droits d’accès ne descendent jamais à ce niveau : on ouvre ou on ferme un onglet entier.

Comment c’est fait

Architecture

L’idée

Une application Shiny au format global.R / ui.R / server.R. Les données sont chargées une fois par processus R, pas par visiteur : le chargement est en tête de server.R, hors de la fonction serveur.

Arborescence

Mazette-Public/
├── global.R          # paquets, source de R/, constantes partagées
├── ui.R              # coquille + un constructeur ui_*() par onglet
├── server.R          # chargement des données puis logique réactive
├── import.R          # reconstruction complète depuis Google Drive
├── R/                # 29 modules, sourcés par global.R (ordre alphabétique)
├── www/              # style.css, icônes, manifest PWA
├── logos/            # logos des brassins
├── outputs/          # cache .RData (ignoré par git)
├── docs/             # cette documentation
└── manifest.json     # manifeste de déploiement Posit Connect

Les modules de R/

global.R source tout R/*.R par ordre alphabétique. Aucun module n’a d’effet de bord au chargement : ce sont des définitions de fonctions et de constantes.

Un point non évident : ui.R et server.R ne se voient pas

Shiny évalue ces deux fichiers dans deux environnements frères, tous deux enfants de l’environnement global. Une fonction définie dans ui.R est donc invisible depuis server.R.

C’est gênant ici, parce que server.R doit appeler les constructeurs ui_*() pour insérer un onglet après la connexion. D’où le petit registre de R/acces.R : ui.R y dépose ses constructeurs, server.R les y reprend. 

# tout en bas de ui.R
enregistre_constructeurs_onglets(environment())

# puis, depuis server.R
nav_insert("nav", panneau_onglet("tab_compta"), target = ..., session = session)

Corollaire pratique : tout ce qui doit être partagé entre l’interface et le serveur appartient à global.R ou à R/, jamais à ui.R.

D’où vient ce qui s’affiche

Les données

Le chemin complet

Classeurs Google Drive → import.R les transforme en une douzaine de tables → celles-ci sont enregistrées dans un .RData, gardé en local et déposé sur Drive → l’application recharge ce fichier au démarrage.

Le chargement se fait en trois étages

Forcer une reconstruction

Passez force_dl = TRUE à l’appel de connexion_ou_creation(), en tête de server.R. C’est le geste à faire après avoir modifié un classeur, si vous ne voulez pas attendre le cache du lendemain.

Les fichiers sources

Rien n’est codé en dur : un classeur d’index (variable ID_DRIVE_PATHS) contient un onglet PATHS à deux colonnes, Path et Link. import.R y lit l’identifiant de chaque fichier. Déplacer une source, c’est modifier une ligne de ce classeur.

Les tables optionnelles

TABLES_OPTIONNELLES, dans le même fichier, liste les tables enregistrées si elles existent, mais dont l’absence n’empêche pas l’import d’aboutir. C’est le sas par lequel une nouvelle source entre dans le dashboard : le volet qui la consomme sait se taire tant qu’elle manque, et on n’est pas obligé de livrer le code et l’import dans le même mouvement.

TableContratÉtat
DB_HEURES_PLANNING Une ligne par DATE × SERVICE, avec HEURES. SERVICE emploie le même vocabulaire de départements que DB_HEURES (« Transfo alimentaire », « Service », « Support »…). à produire L’onglet Planning affiche un bandeau explicatif tant que l’import ne la fabrique pas.
Pourquoi DB_TICKET est stocké en deux morceaux

Six colonnes de DB_TICKET sont entièrement déterminées par ID_PRODUIT. Les répéter sur 245 000 lignes coûtait 1,2 Mo ; le référentiel tient en 843 lignes. Le cache ne garde donc que la forme réduite, et hydrate_dans() refait la jointure au démarrage.

La fonction sait reconnaître un ancien .RData qui contient déjà la forme complète, et le laisse tel quel.

Qui voit quoi

Accès et mots de passe

Le principe

Un mot de passe ne répond pas « oui / non » : il désigne un profil, donc une liste d’onglets. L’accès se joue à l’onglet entier, jamais à l’intérieur d’un onglet.

Les colonnes du classeur

ColonneRôleExemple
Date_debut, Date_finPériode de validité.01/09/2026 → 31/12/2026
passLe mot de passe. Comparaison sensible à la casse, espaces rognés.mazette2026
nomÀ qui il appartient. Affiché en haut à droite une fois connecté.Boris
roleLe profil, qui donne une liste d’onglets.gestion
ongletsOnglets en plus du profil, ou * pour tout. Vide dans le cas général.compta, travail
actifnon coupe l’accès sans effacer la ligne.oui

Les profils

Définis dans la constante PROFILS de R/acces.R : c’est là qu’on ajuste la politique d’accès, sans toucher au tableur.

ProfilOnglets
adminTout, compta et coût du personnel compris.
gestionTout l’opérationnel, Planning compris, sans la compta générale.
equipeL’activité, sans les coûts (ni compta, ni masse salariale).
salleMaintenant, Fûts, Boissons, Réservations.
brasserieMaintenant, Fûts, Boissons.
publicMaintenant, Historique, Année — pour présenter à l’extérieur.
inviteL’accueil et rien d’autre.

Tout le monde a l’Accueil : c’est la page d’atterrissage. Sa grille ne contient que les cartes des onglets autorisés. Un role vide, inconnu ou mal orthographié ne donne que l’accueil : une faute de frappe ferme la porte, elle ne l’ouvre pas.

Ce qui se passe côté serveur

Un onglet interdit n’est pas masqué dans le navigateur : il n’est jamais inséré. Seul l’accueil part avec la page ; après la connexion, le serveur ajoute un à un les onglets autorisés. Le HTML des autres ne quitte pas le serveur et leurs calculs ne se déclenchent jamais.

Ce que ça n’est pas

Un contrôle d’accès applicatif, pas un secret cryptographique. Les mots de passe sont en clair dans un Google Sheet, partagés entre personnes, et transitent en clair si l’application n’est pas servie en HTTPS. C’est adapté à un tableau de bord interne ; ce ne serait pas adapté à des données personnelles ou à un accès public.

La déconnexion (bouton à côté du nom) recharge la page plutôt que de défaire l’insertion. Défaire à la main demanderait de retirer chaque onglet, remasquer les cartes, et de se souvenir de tout ce que la session a accumulé : périodes saisies, prix simulés, lignes sélectionnées. Le rechargement ne peut rien oublier, et ne coûte rien puisque les données sont chargées par processus et non par session.

Rétrocompatibilité

Les quatre colonnes nom, role, onglets et actif sont facultatives. Tant qu’elles n’existent pas dans le classeur — ou tant que le .RData en cache date d’avant — chaque mot de passe conserve tous les droits. C’est colonne_optionnelle() à l’import et normalise_password() au chargement qui s’en chargent.

Reprendre le travail

Administration

Objectif de cette section

Permettre à quelqu’un qui n’a jamais vu le projet de le remonter entièrement : accès Google, variables d’environnement, exécution locale, déploiement, et quoi faire quand ça casse.

Ce qu’il faut avoir sous la main

  • Un accès éditeur aux classeurs Google Drive de la brasserie.
  • Un compte de service Google (fichier JSON) autorisé sur ces fichiers.
  • R 4.5.1 ou proche, et de quoi compiler les paquets.
  • Un hébergement Shiny : Posit Connect, shinyapps.io, ou un Shiny Server.

Installation, pas à pas

  1. Récupérer le code

    git clone https://github.com/tdelc/Mazette-Public.git
cd Mazette-Public
git checkout sql   # branche de référence actuelle
mkdir -p outputs   # le cache y sera écrit ; le dossier est ignoré par git

  2. Installer les paquets R

    Vingt paquets sont chargés par global.R, et cinq de plus sont appelés par :: sans library() — faciles à oublier. 

    install.packages(c(
  # chargés par global.R
  "shiny","bslib","shinyjs","shinyWidgets","shinybusy","dplyr","ggplot2",
  "tidyr","purrr","stringr","tibble","lubridate","googledrive","readxl",
  "scales","plotly","forecast","DT","zoo","patchwork",
  # utilisés via :: uniquement
  "cli","httr","calendar","janitor","htmlwidgets"))

  3. Préparer le compte de service Google

    Dans la console Google Cloud : créer un compte de service, activer l’API Drive, générer une clé JSON. Puis partager chaque fichier Drive avec l’adresse du compte de service, comme on partagerait avec un collègue.

    L’application ne lit pas ce JSON depuis le disque : elle le télécharge depuis l’URL LINK_JSON, l’écrit dans connect.json, puis appelle drive_auth(). Cette URL doit donc être atteignable par le serveur, et rester privée.

    Attention

    connect.json contient une clé privée. Il est déjà dans .gitignore : vérifiez qu’il y reste. Toute personne qui obtient cette URL obtient l’accès aux fichiers.

  4. Créer le classeur d’index PATHS

    Un classeur Drive avec un onglet nommé PATHS, deux colonnes :

    PathLink
    ID_DRIVE_MAZETTEidentifiant Drive du classeur principal
    ID_DRIVE_HEURESidentifiant du classeur des heures
    ID_DB_COMPTAidentifiant de DB_COMPTA.rds
    ID_DRIVE_RESAidentifiant du classeur des réservations
    ICS_SALLEURL du calendrier iCal « salle »
    ICS_TERRASSEURL du calendrier iCal « terrasse »

  5. Déclarer les variables d’environnement

    Dans un fichier .Renviron à la racine (déjà ignoré par git) :

    LINK_JSON=https://.../compte-de-service.json
PATH_DRIVE=<id du dossier Drive où déposer le cache .RData>
ID_DRIVE_PATHS=<id du classeur qui contient l'onglet PATHS>

    En production, ce sont les variables d’environnement de l’hébergeur (sur Posit Connect : Vars, dans les réglages du contenu).

    Trois autres variables, sans effet aujourd’hui

    CF_ACCOUNT_ID, CF_D1_ID et CF_API_TOKEN sont lues par R/sql.R (base Cloudflare D1). Aucune fonction de ce module n’est appelée ailleurs dans le projet : l’application tourne sans elles.

  6. Premier lancement

    R -e 'shiny::runApp(launch.browser = TRUE)'

    Sans cache, la reconstruction complète démarre. La console trace chaque étape (cli::cli_h2). À la fin, un .RData apparaît dans outputs/ et une copie est déposée sur Drive.

  7. Déployer

    Le dépôt contient un manifest.json au format Posit Connect. Il est obsolète (il référence functions.R, supprimé depuis) et doit être régénéré avant tout déploiement : 

    install.packages("rsconnect")
rsconnect::writeManifest()        # régénère manifest.json
# puis publication depuis RStudio, ou :
rsconnect::deployApp()

    Pensez à reporter les variables d’environnement côté serveur : elles ne sont jamais dans le dépôt.

À savoir avant de modifier

Pièges connus

Chacun de ces points a coûté une session de débogage. Ils partagent un trait : ils échouent en silence ou très loin de leur cause.

Les inputs d’un onglet n’existent qu’après son insertion

C’est la conséquence n°1 du contrôle d’accès. Avant la connexion, tous les inputs des onglets valent NULL. Les sorties (render*) ne s’en aperçoivent pas — Shiny ne les calcule que visibles — mais un observe() tourne dès le premier flush. D’où deux règles, selon le sens :

SensRègleSinon
Lire un input d’onglet Le protéger par req(), ou prévoir un repli explicite comme sim_periode_val(). Le calcul part sur NULL : 1 + NULL/100 vaut numeric(0), pas NA.
Garnir un input d’onglet Attendre ONGLETS_PRETS(). Le message vise un champ inexistant : perdu sans erreur, et l’observateur ne rejoue jamais.
Pourquoi le drapeau ne monte qu’au flush suivant

Côté navigateur, Shiny traite ses messages dans l’ordre d’enregistrement de leurs gestionnaires. inputMessages est le 3e, shiny-insert-tab le 19e : garnir dans le même flush que l’insertion remplirait des champs pas encore créés. D’où session$onFlushed(), qui décale d’un cycle.

Dans un observeEvent, le garde-fou va dans le déclencheur

observeEvent() isole son corps. Une dépendance posée là ne rejouera jamais l’observateur quand le drapeau bascule. Elle doit être dans l’expression déclenchante. 

# ne rejoue jamais
observeEvent(base(), { req(PRET()); ... })

# correct
observeEvent({ req(PRET()); base() }, { ... })

$ sur une liste fait de l’appariement partiel

DB_sheets$`IMPORT PASS` trouvait l’onglet IMPORT PASS NEW par préfixe, en silence. Ça marchait — par chance. Le jour où un second onglet commence pareil, le préfixe devient ambigu et $ renvoie NULL sans un mot. Pour un accès par nom, [[ ]] exige une correspondance exacte.

layout_columns() enveloppe chaque enfant

Chaque enfant reçoit son propre div.bslib-grid-item. Masquer l’enfant laisse donc le wrapper — et sa cellule — en place : un trou dans la grille. Pour une grille à géométrie variable, construisez seulement ce que vous voulez afficher plutôt que de masquer.

Un select vide renvoie "", pas NULL

Un selectInput inséré mais pas encore garni renvoie la chaîne vide. Un test is.null() ne l’attrape pas, as.integer("") donne NA, et l’erreur ressort bien plus loin — typiquement un charToDate incompréhensible. Testez la valeur convertie, pas la présence.
